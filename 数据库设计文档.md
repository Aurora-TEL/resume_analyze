# 简历分析系统数据库设计文档

## 1. 文档说明

### 1.1 文档目的

本文档用于描述简历分析系统的数据库设计方案，包括数据表结构、字段说明、主外键关系、索引设计、JSONB 字段结构、数据约束、软删除策略、审计字段和数据库迁移策略。

本文档主要面向：

- 后端开发人员
- 数据库设计人员
- 测试人员
- 部署运维人员
- 项目评审人员

### 1.2 数据库选型

系统数据库采用 PostgreSQL。

选择 PostgreSQL 的原因：

1. 稳定可靠，适合生产环境。
2. 支持 JSONB，适合存储 AI 分析结果和结构化简历内容。
3. 支持事务、外键、索引、唯一约束等关系型数据库能力。
4. 与 SQLAlchemy、Alembic 配合成熟。
5. 适合 Docker 容器化部署。

------

## 2. 数据库设计原则

### 2.1 设计目标

数据库设计应满足以下目标：

1. 支持用户、简历、岗位、分析任务、分析报告等核心业务数据存储。
2. 支持 AI 返回结果的灵活存储。
3. 支持历史记录查询。
4. 支持后续扩展多模型、多报告版本和多任务类型。
5. 支持数据审计、软删除和日志追踪。
6. 支持个人云服务器部署场景下的数据备份与恢复。

### 2.2 命名规范

数据库命名建议：

- 表名使用小写英文复数形式，例如 `users`、`resumes`。
- 字段名使用小写加下划线，例如 `created_at`、`user_id`。
- 主键统一使用 `id`。
- 外键使用 `{关联表单数名}_id`，例如 `user_id`、`resume_id`。
- 时间字段统一使用 `_at` 结尾。
- 状态字段统一使用 `status`。
- JSON 字段使用 `_data` 或 `_json` 结尾。

### 2.3 主键策略

推荐使用 UUID 作为主键。

原因：

1. 适合前后端分离系统。
2. 降低自增 ID 暴露带来的数据枚举风险。
3. 后续数据迁移和分布式扩展更方便。

如果项目希望简化开发，也可以使用 BIGSERIAL。本文档默认使用 UUID。

### 2.4 通用审计字段

核心业务表建议包含以下通用字段：

| 字段       | 类型                     | 说明                 |
| ---------- | ------------------------ | -------------------- |
| id         | UUID                     | 主键                 |
| created_at | TIMESTAMP WITH TIME ZONE | 创建时间             |
| updated_at | TIMESTAMP WITH TIME ZONE | 更新时间             |
| deleted_at | TIMESTAMP WITH TIME ZONE | 删除时间，软删除使用 |

部分表可增加：

| 字段       | 类型 | 说明   |
| ---------- | ---- | ------ |
| created_by | UUID | 创建人 |
| updated_by | UUID | 更新人 |
| deleted_by | UUID | 删除人 |

## 4. 实体关系设计

### 4.1 核心实体关系

```text
users 1 ─── N resumes
users 1 ─── N job_descriptions
users 1 ─── N analysis_tasks
users 1 ─── N analysis_reports

resumes 1 ─── N analysis_tasks
job_descriptions 1 ─── N analysis_tasks
analysis_tasks 1 ─── 1 analysis_reports
analysis_tasks 1 ─── N api_call_logs
prompt_templates 1 ─── N api_call_logs，可选
```

### 4.2 关系说明

1. 一个用户可以上传多份简历。
2. 一个用户可以创建多个岗位描述。
3. 一个用户可以发起多个分析任务。
4. 一个分析任务只能对应一份简历和一个岗位描述。
5. 一个分析任务成功后生成一份分析报告。
6. 一个分析任务可能调用一次或多次 DeepSeek API。
7. 一个 Prompt 模板可能被多个 API 调用日志引用。

## 5. 表结构设计

## 5.1 users 用户表

### 5.1.1 表说明

用于存储系统用户，包括普通求职者用户和管理员用户。

### 5.1.2 字段设计

| 字段名          | 类型         | 约束             | 说明                    |
| --------------- | ------------ | ---------------- | ----------------------- |
| id              | UUID         | PK               | 用户 ID                 |
| email           | VARCHAR(255) | NOT NULL, UNIQUE | 邮箱                    |
| password_hash   | VARCHAR(255) | NOT NULL         | 密码哈希                |
| nickname        | VARCHAR(100) | NULL             | 昵称                    |
| phone           | VARCHAR(50)  | NULL             | 手机号                  |
| avatar_url      | VARCHAR(500) | NULL             | 头像地址，可选          |
| target_position | VARCHAR(100) | NULL             | 目标岗位                |
| target_city     | VARCHAR(100) | NULL             | 目标城市                |
| work_years      | NUMERIC(4,1) | NULL             | 工作年限                |
| role            | VARCHAR(30)  | NOT NULL         | user/admin              |
| status          | VARCHAR(30)  | NOT NULL         | active/disabled/deleted |
| last_login_at   | TIMESTAMPTZ  | NULL             | 最近登录时间            |
| created_at      | TIMESTAMPTZ  | NOT NULL         | 创建时间                |
| updated_at      | TIMESTAMPTZ  | NOT NULL         | 更新时间                |
| deleted_at      | TIMESTAMPTZ  | NULL             | 删除时间                |

### 5.1.3 字段说明

- `email`：作为用户登录账号，必须唯一。
- `password_hash`：只存储加密后的密码，不存储明文密码。
- `role`：区分普通用户和管理员。
- `status`：用于账号禁用、删除等状态控制。

### 5.1.4 索引设计

| 索引名               | 字段       | 类型   | 说明             |
| -------------------- | ---------- | ------ | ---------------- |
| idx_users_email      | email      | UNIQUE | 登录查询         |
| idx_users_status     | status     | NORMAL | 后台筛选用户状态 |
| idx_users_created_at | created_at | NORMAL | 按注册时间排序   |

## 5.4 analysis_tasks 分析任务表

### 5.4.1 表说明

用于记录用户发起的分析任务，包括任务状态、任务类型、开始时间、结束时间和失败原因。

### 5.4.2 字段设计

| started_at         | TIMESTAMPTZ | NULL         | 开始时间                                |

| created_at         | TIMESTAMPTZ | NOT NULL     | 创建时间                                |

### 5.4.3 状态说明

## 5.6 api_call_logs API 调用日志表

### 5.6.1 表说明

用于记录 DeepSeek API 调用情况，便于排查问题、统计调用次数、分析响应耗时和成本。

### 5.6.2 字段设计

| 字段名             | 类型         | 约束     | 说明                    |
| ------------------ | ------------ | -------- | ----------------------- |
| id                 | UUID         | PK       | 日志 ID                 |
| user_id            | UUID         | FK, NULL | 用户 ID                 |
| task_id            | UUID         | FK, NULL | 分析任务 ID             |
| prompt_template_id | UUID         | FK, NULL | Prompt 模板 ID          |
| provider           | VARCHAR(50)  | NOT NULL | 模型供应商，如 deepseek |
| model_name         | VARCHAR(100) | NOT NULL | 模型名称                |
| scene              | VARCHAR(100) | NOT NULL | 调用场景                |
| request_length     | INTEGER      | NULL     | 请求文本长度            |
| response_length    | INTEGER      | NULL     | 响应文本长度            |
| prompt_tokens      | INTEGER      | NULL     | 输入 token 数，可选     |
| completion_tokens  | INTEGER      | NULL     | 输出 token 数，可选     |
| total_tokens       | INTEGER      | NULL     | 总 token 数，可选       |
| latency_ms         | INTEGER      | NULL     | 响应耗时                |
| status             | VARCHAR(30)  | NOT NULL | success/failed          |
| error_type         | VARCHAR(100) | NULL     | 错误类型                |
| error_message      | TEXT         | NULL     | 错误信息                |
| request_id         | VARCHAR(100) | NULL     | 请求追踪 ID             |
| created_at         | TIMESTAMPTZ  | NOT NULL | 创建时间                |

### 5.6.3 安全要求

该表不应存储完整 Prompt 和完整简历内容，以降低隐私泄露风险。

如确需保存请求摘要，应只保存脱敏摘要，例如：

- 请求长度
- 调用场景
- 模板 ID
- 用户 ID
- 任务 ID
- 错误摘要

### 5.6.4 索引设计

| 索引名                       | 字段       | 类型   | 说明             |
| ---------------------------- | ---------- | ------ | ---------------- |
| idx_api_call_logs_user_id    | user_id    | NORMAL | 查询用户调用记录 |
| idx_api_call_logs_task_id    | task_id    | NORMAL | 查询任务调用记录 |
| idx_api_call_logs_scene      | scene      | NORMAL | 按调用场景统计   |

由于系统包含历史分析报告，不建议物理删除核心业务数据。

建议：

1. 用户删除简历时，使用软删除。
2. 用户删除岗位描述时，使用软删除。
3. 分析报告保留历史记录。
4. 管理员可在后台查看删除状态，但默认列表不展示。
5. 只有在用户要求彻底删除个人数据时，才执行物理删除或匿名化处理。

## 9. 软删除设计

### 9.1 软删除字段

涉及用户内容的表建议保留 `deleted_at` 字段：

- users
- resumes
- job_descriptions
- prompt_templates

### 9.2 软删除规则

1. 删除时不直接移除记录。
2. 设置 `status = 'deleted'`。
3. 设置 `deleted_at = 当前时间`。
4. 普通查询默认过滤 `deleted_at IS NULL`。
5. 管理后台可查看已删除数据。

### 9.3 用户数据删除

用户要求删除账号时，可采用以下策略：

1. 将用户状态改为 deleted。
2. 删除或匿名化邮箱、手机号等个人标识。
3. 软删除用户简历和岗位描述。
4. 根据隐私要求删除原始简历文件。
5. 保留必要的脱敏统计记录。

## 10. 数据安全与隐私设计

### 10.1 密码安全

1. 不存储明文密码。
2. 使用 bcrypt 等安全算法保存密码哈希。
3. 登录时只比对哈希结果。

### 10.2 简历隐私保护

简历包含大量个人信息，数据库和日志设计中应避免隐私泄露。

要求：

1. `raw_text` 字段只允许用户本人和授权管理员访问。
2. API 日志不得保存完整简历内容。
3. 错误日志不得输出完整简历文本。
4. 管理员查看简历原文应记录操作日志。
5. 用户删除简历时，应同步处理原始文件。

### 10.3 敏感字段处理

敏感字段包括：

- password_hash
- phone
- email
- raw_text
- file_path
- DeepSeek API Key，不入库

返回给前端时应避免返回：

- password_hash
- 完整文件路径
- 系统内部错误堆栈
- API Key

## 11. Alembic 数据库迁移设计

### 11.1 迁移工具

后端使用 Alembic 管理数据库结构变更。

### 11.2 迁移原则

1. 每次表结构变更都生成迁移文件。
2. 迁移文件应提交到代码仓库。
3. 生产环境发布时执行迁移命令。
4. 不直接手动修改生产数据库表结构。
5. 大字段调整需注意数据备份。

### 11.3 常用命令

```bash
# 初始化 Alembic
alembic init migrations

# 自动生成迁移文件
alembic revision --autogenerate -m "init tables"

# 执行迁移
alembic upgrade head

# 回滚上一个版本
alembic downgrade -1
```

### 11.4 Docker 环境执行迁移

开发环境：

```bash
docker compose exec backend alembic upgrade head
```

生产环境：

```bash
docker compose -f docker-compose.prod.yml exec backend alembic upgrade head
```

## 16. 数据库性能建议

### 16.1 分页查询

所有列表接口应使用分页查询，例如：

- 简历列表
- 岗位列表
- 分析报告列表
- API 调用日志列表
- 用户列表

### 16.2 避免大字段频繁查询

以下字段属于大字段：

- resumes.raw_text
- resumes.structured_data
- job_descriptions.description_text
- analysis_reports.report_data

列表查询时不应默认返回这些字段，应在详情接口中按需查询。

### 16.3 日志表归档

`api_call_logs` 可能持续增长，后续可按月归档。

建议：

1. 后台默认查询最近 30 天日志。
2. 定期归档历史日志。
3. 生产环境避免无限制查询日志全表。

## 18. 总结

本数据库设计围绕简历分析系统的核心业务展开，重点支持用户管理、简历管理、岗位描述管理、AI 分析任务、分析报告、Prompt 模板和 API 调用日志。

后续开发时，建议以本文档为基础创建 SQLAlchemy 模型，并使用 Alembic 生成数据库迁移文件。
